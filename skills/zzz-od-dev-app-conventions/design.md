# zzz-od-dev-app-conventions 设计与决策

## 为什么做
这份规范来自一次完整的应用开发:新增"空洞周期速刷"(固定副本的速刷模式,先做成枯萎之都的运行模式,后拆成独立应用)。开发中用户多次指出"不符合框架实践",每次都是智能体按自己的习惯写了框架已有等价物的东西。把这些反馈归并成规范,避免下次重复犯。

## 定位与边界
- 管:新增或修改应用、操作、设置页、画面区域配置时的**写法与验证**,以及评审时的检查表。
- 不管:应用的文件结构与命名(归 `zzz-od-dev-plugin`)、新画面的拍摄与建档(归 `zzz-od-dev-screen-onboarding`)、实机问题的排查方法(归 `zzz-od-dev-debug-automation`)。这些在 SKILL.md 开头引用,不重复。
- 游戏事实(具体按钮、坐标、玩法)不进 SKILL.md,按 skill 规范归 doc。本文件可以举例,因为它只给维护者看。

## 规范与来源对照
| 规范 | 当时用户的反馈 / 出现的问题 | 决策理由 |
|---|---|---|
| 1 先复用 | 用户问"黑洞格、S 门、业绩格不能复用已有的吗?";关闭按钮要用通用模板 | 我一开始列了一堆要手工做的模板,其实地图识别模型的类别表里早就有。先查再要,省用户的手工 |
| 2 区域进 screen_info | 要求邦布插件区域"走 screen";关闭按钮"不应该 OCR X" | 区域放配置里才能被画面系统、调试工具共享,代码里写矩形常量没人能发现和修改。运行时读的是合并文件,只改单独 yml 会不生效 |
| 2 换行符 | 仓库文件是 CRLF,直接编辑会混入 LF | 混合换行会让 diff 全文件变更,评审困难 |
| 3 用 round_by_* | "get_area 这种模块内部封装不太符合框架实践" | Operation 已有对应的 round_by_* 方法,自建封装既重复又让读代码的人要多学一套 |
| 4 无模块级变量 | "模块级变量也不太符合框架实践" | 常量用类级 ClassVar 与框架现有写法一致;跨操作的缓存放上下文,能随运行重置,可变类变量会在多次运行间泄漏 |
| 5 不绑定应用 | 拆分独立应用时发现 app_id 在 12 处被写死 | 共享代码写死具体应用,拆应用或复用时就要大改。让上下文记录当前 app_id,代价小得多 |
| 5 继承 + 钩子 | 速刷最初作为运行模式加在原应用里,模式开关渗进共享代码 5 处以上 | 模式开关越积越多、回归风险大;继承钩子把差异收在子类里。同时用户希望两者能同时排进一条龙,这是拆分的决定性理由 |
| 6 设置页 | "去掉不需要的配置项""每天和每周次数摆一起""desc 技术细节不用说" | 用户只关心他能调什么;固定值做成设置项只会增加困惑 |
| 6 改名 | 名称连改三次,配置里存的是选项字符串 | 选项值即显示文字,改名会让已保存的值落回默认,必须提示 |
| 7 自适应与后摇 | 长按/点击含义可被玩家交换;使用后有后摇导致下一次点击无响应,被误判失败 | 无法从画面判断玩家设置,只能按结果自适应并记住;已知有效手势时失败应重试同一种,否则后摇会把状态弄乱 |
| 7 不依赖调试模式 | 调试开着时"点最下面选项"的兜底被关闭,导致事件卡死 | 兜底行为不该由调试开关隐式控制,要显式传参 |
| 8 验证 | 多次用桩对象测决策逻辑、全量扫选项表、完整初始化 smoke test | 无法在游戏里跑时,把可测的逻辑尽量测掉,并清楚说出未验证部分 |
| 8 清理测试产物 | smoke test 创建了配置目录和运行记录 | 污染用户的实例配置会让用户看到莫名的记录 |
| 9 同类一次改完 | 用户连续两条评论分别指出封装和模块变量,本质同一类问题 | 只改被点到的一处会让用户反复评审同一类问题 |

## 关键决策
- **检查表而非流程**:这是写代码时的对照清单,不规定从需求到发布的整套流程(那是各 workflow skill 的事)。
- **允许写的接口名**:`round_by_*`、`@operation_node`、`@node_from`、`screen_loader.get_area`、`get_prop_adapter` 是框架地基级接口,按 skill 规范 3 可直接写全名;具体业务代码文件和行号一律不写。
- **含 `.log/log.txt`、`_od_merged.yml`、`labels.csv` 路径**:它们是 skill 要读写的稳定运行时资产,不是易变的实现细节。
- **"拆分前先确认"**:拆分会动共享代码和设置界面,风险高于普通修改,所以要求先问用户。
- **没有做 RED baseline**:属于方法论覆盖型加纠正型混合,纠正部分直接来自用户的真实反馈。GREEN 验证(用该 skill 实际开发一个新应用,看产出是否符合清单)尚未做,首次使用时应观察。

## 落点
- 目录 `skills/zzz-od-dev-app-conventions/`,开发类 skill 使用 `zzz-od-dev-` 前缀。
- Claude Code 发现需要本地 junction `.claude/skills/zzz-od-dev-app-conventions`(不提交)。
