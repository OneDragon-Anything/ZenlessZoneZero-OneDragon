# design: zzz-od-dev-plugin

## 为什么做

新增内置应用和第三方插件时，需要同时处理目录结构、const 字段、工厂注册、应用实现、运行记录、设置界面和画面配置。若只参考某个现有应用，容易把该应用的偶然实现当成框架要求，也容易漏掉插件扫描和入口边界。因此把稳定的开发判据整理成项目 Skill，作为新增或修改应用插件时的统一执行入口。

## 定位与边界

- **管**：内置应用与第三方插件的文件组织、const 与工厂契约、入口字段选择、运行记录选择、设置界面和插件画面配置的接入检查。
- **不管**：具体游戏玩法、坐标、画面事实和业务流程；这些内容分别进入玩法、画面和应用开发文档。
- **不替代架构文档**：Skill 只保留智能体实际开发时必须执行的方法和判据；插件系统的完整调用链与字段说明仍由正式开发文档维护。
- **不承担发布管理**：第三方插件如何分发、版本发布和用户安装不在本 Skill 的核心范围内。

## 关键决策与理由

### 1. 内置应用与第三方插件共用 ApplicationFactory 契约

两类应用都由同一套工厂扫描和运行上下文注册。Skill 先讲共同契约，再标出导入方式和存放位置的差异，避免为第三方插件复制一套容易漂移的开发流程。

### 2. DEFAULT_GROUP 与 INTERNAL_APP 只表达入口范围

`DEFAULT_GROUP` 只决定应用是否默认进入一条龙；`INTERNAL_APP` 只决定应用能否从 GUI、后端、HTTP、MCP 的通用独立应用入口选择。两个字段不定义业务进度或自定义运行周期。一条龙需要每日完成判断，因此父工厂依据 `DEFAULT_GROUP` 提供基础每日记录；这不禁止非一条龙应用自行提供业务记录。

这样保留三个明确组合：

- 默认一条龙应用：`DEFAULT_GROUP=True`、`INTERNAL_APP=False`；
- standalone 应用：`DEFAULT_GROUP=False`、`INTERNAL_APP=False`；
- 固定入口应用：`DEFAULT_GROUP=False`、`INTERNAL_APP=True`。

`True/True` 没有合理含义：一个应用不能既默认进入一条龙，又要求不出现在任何通用列表，所以在加载时直接拒绝。`INTERNAL_APP` 保持可选并默认 `False`，是为了让旧 const 的 `DEFAULT_GROUP=False` 自然映射为 standalone，而不要求旧插件立即改文件。现有内置固定入口应用必须显式声明 `INTERNAL_APP=True`，避免被新语义暴露。

internal 是产品入口限制，不是底层权限。底层 `run_application()` 必须继续允许运行已注册的 internal 应用，否则专用页面、父应用调用子应用和系统固定入口都会失效。

### 3. 基础运行记录由父工厂默认创建

一条龙需要知道应用在当前游戏日是否已经成功，所以 `DEFAULT_GROUP=True` 的应用即使没有业务进度，也要有基础每日记录。父工厂为这类应用创建基础 `AppRunRecord`，并从具体工厂保存的上下文读取当前区服刷新偏移。

`DEFAULT_GROUP=False` 的应用不参与一条龙的每日跳过判断。没有自定义记录时返回 `None`，这是正常状态，不能抛出“未创建记录”之类的错误。

不修改 `ApplicationFactory.__init__()` 的构造协议。具体工厂本来就接收上下文并保存 `self.ctx`，父类只把这一事实声明为子类契约，避免为默认记录批量改造所有工厂构造函数。

只有基础每日记录无法表达需求时才覆盖 `create_run_record()`，例如每周重置、业务进度、自定义完成判定。覆盖方法自身的创建异常仍要暴露，避免用空记录掩盖真实失败。

手动运行与一条龙共享账号下的应用记录。记录表示应用是否完成，不表示从哪个入口完成；手动成功后允许一条龙跳过。不额外维护自动执行专用状态，避免没有明确需求就分裂业务完成语义。

### 4. SKILL.md 只保留可执行判据

操作步骤、字段选择和最小语法必须直接写在 `SKILL.md`，不能要求智能体读取本文件才能完成任务。本文件只保存设计理由、边界和容易被后续修改破坏的决策背景。

对外部代码只使用框架地基级接口名和稳定的运行时资产位置。需要寻找实现模式时，要求在项目中搜索现有做法，不固化某个具体应用文件或行号，避免代码移动后 Skill 静默过期。

## 落点

- Skill 本体位于 `skills/zzz-od-dev-plugin/`，由项目版本管理并供不同智能体工具复用。
- `SKILL.md` 是执行入口；`design.md` 是维护者理解设计原因的记录，不进入任务执行流程。
- 插件源码仍按类型放在 `src/zzz_od/application/` 或 `plugins/`；正式架构说明放在 `docs/develop/`，不写入 Skill 目录。

## 验证方式

修改本 Skill 后逐条检查项目 Skill 的四项硬规范：存在 `design.md`、正文使用指令和判据、引用内容可随项目稳定获得、具体业务事实不进入执行说明。再用一次新增或修改插件的场景检查：智能体应能正确选择入口字段、默认复用基础运行记录，并只在确有业务需要时创建自定义记录。
