# 设计说明

## 为什么做

给 `color_range` 取值时，靠肉眼看截图猜颜色不准：同一状态在不同光效、不同背景下的像素会漂移，单帧取样得到的区间偏窄，填进配置后实机识别会漏。需要一个能持续采样、按模板掩码过滤、同时给出 RGB 与 HSV 的工具。

## 定位与边界

只管「已有模板的颜色采集」。模板点位怎么定、该用哪种检测方式、检测代码怎么改，都不在这个 skill 范围内。

## 关键决策

### 要求绝区零在前台，否则一帧不采

绝区零切到后台时，`PrintWindow(PW_RENDERFULLCONTENT)` 返回全黑，`BitBlt` 与 `PIL` 拿到的是桌面。这三种方式采到的都不是游戏画面，采出来的颜色毫无意义。所以判据用 `ctx.controller.game_win.is_win_active`，为假时整轮跳过。

不采用「先截一张，检测是不是黑图」的试探：黑图只是后台表现之一，桌面残留也可能不是黑的，试探判据不可靠，还容易把桌面颜色混进累积区间。

### 按模板掩码取像素，而不是取整块区域

模板的掩码本身表达了「哪些像素属于这个状态」。区域里还有背景、进度环、其他 UI 元素，取整块会把它们算进来，区间被无关颜色撑宽。

注意 `bitwise_and(part, part, mask=...)` 会把被遮像素置 0，0 也会被当成一种颜色统计进去。所以脚本不用涂黑结果，而是直接用 `mask > 127` 取出有效像素再统计。

### 同时输出 RGB 和 HSV

配置里两种颜色范围都有在用，采集一次两套都拿到，避免为同一次采样跑两遍。

H 通道按 OpenCV 约定是 0~179，不是 0~359。

### 只给全区间，不给 5%~95% 主区间

早期版本同时输出「全区间」和「去掉两端各 5% 的主区间」，理由是主区间更接近状态稳定时的颜色，配出来不容易误命中。

这个取舍在状态检测上不成立：**状态检测要的是绝对稳定**，被剔掉的那 5% 同样是真实出现过的像素，照着主区间填就会漏检——状态明明在，识别却报没有，比偶尔多认一次坏得多。所以脚本只输出一组覆盖全部采样点的值，「别漏」由区间宽度保证，「别误命中」交给实机复验同一块区域在状态不显示时的颜色。

### 持续采样，但默认只采 5 秒

状态颜色会随光效、背景、受击闪白变化，单帧采样只能代表那一个瞬间。

实测状态图标这类纯静态色，区间从第二秒起就不再变化，采 5 秒与采 30 秒结果完全一致。所以默认 5 秒，需要覆盖动态光效时用 `--duration` 加长，传 0 表示一直采到 Ctrl+C。

### 直接输出可填的 `hsv_color` 与 `hsv_color_diff`

只给区间最小最大，使用者还要自己算中心和半宽，容易算错也容易嫌远。脚本结束时把区间反推成「中心色 + 容差」，两行直接对应 `AgentStateDef` 的两个参数。

**H 必须按环形处理**：H 是 0~179 的循环量，`min~max` 在这个通道上没有意义——采样同时落在 178 和 2 时，上下限会被写成 2~178，把中间所有色相都圈进来。脚本用最大间隙法：排序采样、找相邻差里最大的那段缺口，中心取缺口对面的中点，容差取剩余跨度的一半。

S 与 V 是线性量，按中点与半宽换算。
