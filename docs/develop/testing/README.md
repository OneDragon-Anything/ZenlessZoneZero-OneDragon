# 测试方法论

贝果测试按关键业务行为组织，日常检查和完整回归见[贝果测试入口](bagel.md)。本页逐方法组织、逐节点分支检查的要求不强制用于贝果；同一行为优先在能稳定验证它的最高层检查。

测试代码位于独立仓 `zzz-od-test`。主仓不保留测试。本页说明环境、测试选择、测试编写和提交要求。

## 1. 准备与运行

1. 将[测试仓](https://github.com/OneDragon-Anything/zzz-od-test)克隆到主仓根目录，目录名为 `zzz-od-test`。
2. 在开发工具中，将该目录设为测试源目录（`Test Sources Root`）。
3. 按所运行测试的需要，将测试仓 `.env.sample` 的变量配置到主仓 `.env`。已有文件先核对，不直接覆盖。
4. 在主仓根目录运行：

```powershell
uv run --env-file .env pytest zzz-od-test/
```

新测试放在测试仓 `test/` 中与被测包对应的位置，不放回主仓。

## 2. 测试基础设施

测试夹具（fixture）是 pytest 为测试准备和清理依赖的函数。文字识别简称 OCR；`screen_info` 是画面区域与识别参数资源。

测试仓 `test/conftest.py` 提供以下能力：

| 对象或方法 | 用途 |
| --- | --- |
| `test_context` | 在整个测试会话中初始化一次上下文，加载真实 OCR 和画面资源，注入模拟控制器 |
| `current_instance_idx=99` | 将测试配置写入与正常账号不同的实例 |
| `test_context.add_mock_screenshot(img)` | 将指定图像设为控制器的下一帧 |
| `test_context.mock_screen(screen_name, state)` | 读取 `screens/<画面>/<状态>.webp` 并设为下一帧 |
| `MockController` | 截图返回模拟帧；点击只返回坐标是否在有效范围内，不向游戏输入 |
| `FixtureController` | 根据模拟输入切换截图，用于执行多帧流程 |

素材格式见[素材归档规范](../zzz/screenshot_archive.md)。流程控制器的使用方法见[FixtureController 说明](fixture_controller.md)。

## 3. 确定测试范围

应用（Application）由操作（Operation）及其节点组成。节点返回的 `status` 表示状态；下游 `@node_from` 声明哪些状态可以进入该节点。

除贝果的专项组织规则外，一个应用或操作须完成以下检查：

1. 为每个节点的每个业务分支编写单元测试。
2. 节点返回 `round_wait` 或使用 `until_*` 条件时，另写流程测试。
3. 编写测试时，将上游返回状态与下游 `@node_from` 声明逐项对照。

框架加载时校验节点和边是否合法，以及开始节点是否唯一。应用测试不重复检查这些框架职责。

### 识别节点分支

| 节点写法 | 如何确定分支 |
| --- | --- |
| 显式返回状态 | 检查 `round_success/wait/retry/fail` 中可能返回的状态 |
| 只调用辅助方法 | 阅读辅助方法的返回条件，不能仅看节点方法体 |
| 条件判断后调用辅助方法 | 同时检查显式条件和辅助方法的返回条件 |
| 委托子操作 | 在子操作中验证业务分支，并检查父操作如何接收结果 |

常见辅助方法的返回条件如下。此表不是完整清单，实际实现以操作框架代码为准。

| 辅助方法 | 返回条件 |
| --- | --- |
| `round_by_ocr_and_click_by_priority` | 匹配目标时成功；未匹配目标时重试 |
| `round_by_find_area` | 命中区域时成功；未命中时重试 |
| `round_by_find_and_click_area`，未设置 `until_*` | 点击成功时成功；未找到或点击失败时重试；区域未配置时失败 |
| `round_by_find_and_click_area`，设置 `until_*` | 点击后先等待；下一轮满足条件时成功 |
| `round_by_op_result` | 传递子操作结果，本身没有额外业务分支 |

区域未配置属于配置错误，通常不另写应用测试，但识别分支时必须知道该返回条件。

每个业务分支用对应输入触发，断言返回状态和动作。不能只检查成功布尔值，具体返回类型见第 5 节。

### 对照下游状态

1. 搜索当前节点对应的所有 `@node_from(from_name=...)`。
2. 只对照 `round_success` 和 `round_fail` 的返回状态。`round_wait` 与 `round_retry` 在当前节点内部等待或重试，不进入下游边。
3. 检查下游声明的状态能否由上游返回。不能返回时，核对拼写、实现和测试。
4. 检查上游返回状态是否有下游接收。无精确匹配时，还要检查 `ignore_status=True` 的默认边和终止状态。
5. 对指定状态的失败边，用失败场景验证其可达性。状态来自子操作时，检查子操作的返回条件。

不使用静态扫描工具猜测全部返回状态。辅助方法可能动态生成状态，子操作也可能直接传递状态，静态猜测会漏报或误报。此检查依赖编写者和评审者逐项核对，尚无自动化持续保证。

### 选择流程测试

返回 `round_wait`，或使用 `until_find_all`、`until_not_find_all` 时，用 `FixtureController` 执行完整 `execute()`，验证点击、等待、画面变化和后续识别。

只有 `round_retry` 不表示一定需要多帧流程测试。例如，未找到目标或点击失败可以在同帧重试。直接委托子操作的节点不重复编写子操作的业务测试。

流程测试补充节点单测；除贝果的专项规则外，它不替代逐分支检查。运行状态、超时保护、恢复点击、游戏启动隔离和剪贴板处理见[流程测试说明](fixture_controller.md)。

### 提交前自检

- [ ] 节点业务分支已有断言，包括辅助方法返回的分支。
- [ ] 等待画面变化的节点已有流程测试。
- [ ] 上下游成功和失败状态已逐项对照。
- [ ] 未完成的测试和实机验证范围已明确记录。

## 4. 测试职责

| 对象 | 验证方式 |
| --- | --- |
| 节点和边的结构合法性 | 框架加载校验 |
| 单节点识别、决策和业务分支 | 模拟输入，直接调用节点 |
| 多帧等待、重试和恢复 | 用流程控制器执行完整操作 |
| 上下游状态匹配 | 单测断言与人工对照 |

框架只检查结构，不能代替业务状态和画面推进测试。没有多帧等待的应用不必为满足形式要求编写完整流程测试。

## 5. 编写单节点测试

先阅读节点检测的画面、文字和区域，再选择模拟帧。状态名称可以帮助定位，但不能代替阅读实现。

```python
def test_example(test_context: "TestContext") -> None:
    test_context.mock_screen('打开游戏', 'ready')
    op = SomeOp(test_context)
    op.screenshot()
    result = op.check_screen()
    assert result.status == '打开游戏'
```

上例只展示调用顺序。实际测试导入对应操作类和测试上下文类型。

| 返回类型 | `is_success` | 断言重点 |
| --- | --- | --- |
| `round_success` 或识别命中后返回成功 | `True` | 成功状态和动作 |
| `round_wait` | `False` | 等待状态和已发送动作 |
| `round_retry` | `False` | 重试状态和禁止发送的动作 |

不同节点即使检测相同目标，也可能返回不同类型，不能照搬断言。

测试失败时，先核对检测目标。例如，节点检测入口菜单中的「好物铺」选项时，不能用好物铺内部标题替代。相似文字可能通过最长公共子序列（LCS）匹配误命中；构造未命中场景时，要排除这种文字干扰，不能为取得通过随意换图。

仅包装辅助方法的节点，检查命中和未命中。带额外条件的节点，还要检查该条件，例如 `claim=False` 时返回“跳过收获”。

配置分支优先通过 `monkeypatch.setattr` 修改配置类属性，不写入磁盘。pytest 在测试结束后恢复属性；测试实例使用 99，避免影响正常账号。

### 验证等待条件

`until_find_all` 或 `until_not_find_all` 需要在同一个操作实例上连续调用节点两次：

1. 设置点击前画面，截图并调用节点。检查点击与 `round_wait`。
2. 设置点击后画面，再次截图并调用同一节点。检查条件满足后返回成功。

不要在两次调用之间重建操作。完整执行器进入新节点时会重置 `node_clicked`；直接连续调用节点则保留该标志。单帧模拟不能用于无限等待画面变化的完整执行。

## 6. 编写流程测试

需要验证画面推进时，用 `FixtureController` 执行完整操作。控制器模拟游戏对输入的反应，不连接真实游戏。

流程测试检查节点衔接、轮询、重试和恢复。运行前提、终止保护和示例统一见[FixtureController 说明](fixture_controller.md)。

## 7. 分仓提交

测试属于独立仓。主仓忽略 `zzz-od-test/`，因此必须分别暂存和提交，不能只提交主仓。提交授权和两仓协作规则见[项目入口](../../../AGENTS.md)。

已获提交授权时，在测试仓提交修改：

```powershell
git -C zzz-od-test add test/
git -C zzz-od-test commit
```

## 8. 文件和代码要求

- 按被测包路径和模块组织测试。除贝果专项规则外，一个测试文件检查一个方法的不同场景。
- 用 pytest 夹具管理依赖，并明确其有效范围，例如整个测试会话共用的 `test_context`。
- 导入使用实际包名，不以 `src` 为包名前缀。
- 异步测试设置超时，例如 `@pytest.mark.timeout(3)`，防止无限等待。
- 仅对修改的 Python 文件运行 Ruff。
- 素材格式、精度、尺寸例外、来源和迁移统一遵循[素材归档规范](../zzz/screenshot_archive.md)。精度敏感样本不得统一有损压缩。
