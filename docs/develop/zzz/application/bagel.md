# 贝果计划（自动化方案）

本文说明贝果计划的脚本流程、配置、使用前提和设计决策。玩法见[玩法说明](../../../game/gameplay/贝果计划.md)，画面见[画面说明](../../../game/screens/贝果计划.md)。

**启动清空。** 每次启动任务时，正式应用仅在首次入场前允许自动清空携带物。

| 携带状态 | 脚本动作 |
| --- | --- |
| 背包和安全箱均为空 | 快速双击备战右侧的已装备槽位，逐件卸下物品 |
| 背包或安全箱有物品 | 先在仓库点击「放入仓库」转存内容物，再返回备战卸下已装备物品 |

首次入场前的清空也包括仓库中的遗留携带物。同次运行的后续各局只检查携带状态。发现非零携带时，正式应用停止运行。范围、停止条件、识别方式和实机验证限制见[启动时自动清空战备](bagel_clear_loadout.md)。

**当前范围。** 正式应用只执行雅努斯高危难度，入场要求零携带和零投资。零携带指武备、装备和道具价值均为 0，且背包和安全箱均为零占用。零投资指投资金额明确为 0。

| 出生点 | 收集路线 |
| --- | --- |
| 录像店复活点 | 武备箱，然后电子保险箱 |
| 白鸽工地地铁站复活点 | 只开武备箱 |
| 单廊双容器复活点 | 跑到录像店复活点，再按录像店的固定流程收集 |
| 其他出生点 | 退出重开，不清理仓库 |

正式应用不投资、不购买。贝果任务位于一条龙列表中，排在驱动盘拆解之后、通知之前。已保存的一条龙顺序保持原样。新加入列表的贝果任务默认关闭，启用后才与其他日常任务一起排队。

## 1. 脚本流程

`BagelApp` 从已识别且允许启动的画面进入研究站，循环执行到成功次数上限。默认上限为 1，设置为 0 时不限制成功次数。

1. 校验配置，并加载三个支持出生点的发布流程（`flow.yml`）。本次执行固定使用已加载的步骤和路点，称为流程快照。
2. 根据当前画面进入研究站入口或选图页。首次启动时若在贝果仓库，先转存携带物，再返回备战或研究站入口。该转存不调用结算出售，也不增加成功局数。各起点的处理规则见[入场与携带核验](#入场与携带核验)。
3. 选择并核对雅努斯高危，进入备战页。同一次任务已经成功入仓过时，默认仍是这一组地图和难度，可跳过点击直接进备战；进页后若发现页签不符，退回逐项点击重新选择。
4. 核对当前画面的零携带状态。首次入场可以先清空非零携带，再复核零携带。后续各局发现非零携带时停止。
5. 核对零投资并入场。
6. 用小地图识别出生点，执行对应路线。
7. 主动退出到仓库，核对安全箱物资入仓，再按清理开关处理仓库。
8. 核对结算结果，更新成功局数，决定结束任务或开始下一局。

录像店路线依次执行：靠近武备箱、开箱、装入安全箱、靠近电子保险箱、交互开箱、完成光圈解锁、再次装入安全箱、主动退出、入仓和按开关清理。

白鸽工地地铁站路线依次执行：靠近武备箱、开箱、装入安全箱、主动退出、入仓和按开关清理。导航使用小地图匹配位置并沿路点移动，不提供遇敌恢复。

单廊双容器路线依次执行：跑向录像店复活点（8 个移动段）、武备箱开箱装入、跑向电子保险箱、解锁装入、主动退出、入仓和按开关清理。**跑到录像店复活点之后的收集段与录像店路线逐字相同** —— 同样的动作顺序、同样的导航参数，只有路点坐标按两图固定平移换算过。开箱、解锁、入仓和收尾共用同一套实现。路点和移动参数以[单廊双容器发布流程](../../../../assets/game_data/bagel/janus_high_c/flow.yml)为准。

其他出生点退出并返回入口，不清理仓库，也不增加成功局数。出生点重选没有尝试次数上限。

寻路卡位、定位失败、局内步骤或操作超时、被敌人击杀、容器恢复失败，以及搜查或解锁中断，均进入失败收尾。正式应用释放输入、记录原因和截图，再根据新画面退出到仓库。核对安全箱入仓并按开关清理后，正式应用才决定是否消耗整体重试次数重开。次数耗尽时，应用仍先完成结算，再停在仓库。失败局不计成功。详细规则见[整体重试说明](bagel_failure_retry.md)。

| 结算结果或配置 | 计数和后续动作 |
| --- | --- |
| 安全箱有物，已确认入仓并完成清理 | 增加 1 个成功局数。清理关闭时，只需完成入仓和结算核验 |
| 安全箱为空 | 返回研究站入口，不增加成功局数。连续 3 次空箱后停止。不进入出售流程 |
| 成功次数上限为正数，且已达到上限 | 任务成功结束 |
| 成功次数上限为 0 | 继续执行，仍受失败、异常和连续空箱停止条件限制 |
| 入仓失败、清理失败或清理后仍满仓 | 停在当前画面，不开始下一局 |
| 入仓时仓库已满，安全箱仍有物资 | 无视清理开关先出售腾位（允许安全箱非空），腾位后补入仓，直到物资真正入库 |

## 2. 设计决策

### 入场与携带核验

**多画面入场边界。** 正式应用根据启动画面选择入口：

| 当前画面 | 处理 |
| --- | --- |
| 贝果入口或选图页 | 继续现有入场流程 |
| 备战页 | 先返回选图，再重新选择并核对雅努斯高危 |
| 首次启动时的贝果仓库 | 按[启动清空流程](bagel_clear_loadout.md)转存携带物，核验后返回 |
| **贝果结算页或退出确认页** | **先点掉再继续**：结算页点「继续」、退出确认点「确认」，然后重新判定入口 |
| 普通大世界、地图、菜单、快捷手册、普通仓库或达塔对话 | 复用返回大世界和地图传送流程，传送到奥蒙德研究站「迷宫诡域」 |
| 未识别画面，且未发现战斗 HUD | 正式应用尝试[页面阻挡恢复](bagel_failure_retry.md#页面阻挡恢复)。独立入场工具直接停止 |
| 已识别的战斗或其他玩法局内 | 停止并保留现场，不自动退出 |

**贝果残留画面自动恢复。** 上一次运行可能停在局内结算页或退出确认页，例如手动打完一局没有点「继续」。这两种画面能被识别，但不在允许进入的画面范围内，直接判定会永久停机并留下现场。入场操作在判定入口前先检查这两页：命中就点掉它（结算页点「继续」，退出确认点「确认」），等待画面变化后重新走入口判定。只处理带明确文字按钮的贝果自己的画面，不碰其他应用画面，也不碰局内战斗 HUD。实测已归档的结算页截图均能正确命中，局内与仓库画面均不误判。

启动时已在达塔前或达塔对话中，正式应用也先返回大世界并进行地图传送。达塔对话仅用于确认这是允许传送的已知画面，启动时不点击「出发出发」。本次传送完成后，正式应用才识别达塔并交互打开入口。两个起点因此共用同一套入场动作。

地图传送失败时，正式应用立即停止。页面阻挡恢复后仍不能继续时，正式应用也停止并保留现场。

音擎仓库和驱动仓库属于其他应用的局部画面。全局识别失败后，贝果入场操作按完整仓库标题补充识别。标题区域配置缺失时，操作跳过该项并检查其他仓库。普通仓库不能作为贝果结算仓库处理。

**入场只核对当前携带。** 入场前，备战页五项携带读数必须明确符合零携带条件。识别不全时，操作最多读取 5 帧，期间不操作物品。持续识别不明时停止。只有正式应用每次启动的首次入场允许先清空非零携带。

仓库可以有库存。自动收集还需要满足允许执行的画面条件和零投资条件，并完成本局结算核验。

**后续局遗留物资禁止开新局。** 首次启动可以转存仓库中的携带物，但不计成功。同次运行的后续入场前，若仍在结算仓库且安全箱有物资，正式应用停止并保留现场。

首次清空资格在第一次入场前消耗，不等待出生识别或局数增加。暂停和恢复不重置该资格。任何启动清空失败都直接停止，不自动出售物品腾出仓位。

### 价值读取

按以下顺序读取武备、装备和道具价值：

1. 识别备战右侧完整面板，排除左侧库存。从结果中筛选三个标题条区域。对应标题完整匹配，且数值恰好是一段纯数字时，采用该结果。
2. 面板结果不满足条件时，裁出完整标题条重新识别。优先采用唯一一段纯数字。没有纯数字时，才从唯一一段「1–2 个非数字前缀 + 完整数值」中提取数字。
3. 裁图结果仍无法解析时，识别整屏。结果必须同时满足标题匹配和数值为唯一一段纯数字。
4. 所有读取方式均无法解析时，返回空字符串，按未知状态处理。

判为零前，识别函数核对该区域所有已获得的文字。任一结果包含非零数字时，函数返回空字符串，拒绝零携带入场。例如，`0` 与 `@500` 同时出现，或面板读到 `500` 而标题条裁图只剩 `0`，均不能放行。

标题条必须包含完整数值，不能只截末尾。价值读取不使用亮白过滤，避免道具价值 `0` 被读成 `O`。

背包、安全箱和投资金额分别裁出各自的完整区域读取。投资金额继续使用独立的颜色过滤和严格零值校验。

投资金额区域左边界要避开金额左侧的金币图标。图标高光与白色数字亮度接近，颜色过滤无法区分；框只要包含图标，OCR 就会把图标轮廓读成数字，使零投资变成 `20` 之类的非零读数，白点三次 MIN 后报「无法确认零投资」。金额非零时数字在金币右侧，图标与数字的相对位置不变，因此收窄左边界不影响 `500K`、`1.5M` 等读数。

### 投资金额归零

识别到投资页后，操作读取完整金额并决定动作：

| 读数 | 动作与完成条件 |
| --- | --- |
| 正整数，或带 `K/M` 的正数，如 `500K`、`1.5M` | 点击 MIN。点击成功后等待 1 秒，下一轮重新截图读取金额 |
| 初始金额或复核金额精确为 `0` | 点击「前往空洞」。点击成功后，才记录投资已确认 |
| 空值、`O`、`00` 等不明确读数 | 只重新读取，不发送输入 |

点击 MIN 成功不表示金额已归零。非零归零和读数不明共用 3 次重试预算。MIN 未识别或点击失败也消耗 1 次。预算耗尽后，操作再读 1 帧。金额仍不是 `0` 时，操作停止并保存现场。

投资重试预算单独记录，避免节点等待重置框架重试次数。重复执行时，预算清零。点击入场后，操作不重复归零或确认。

**零携带弹窗连续确认。** 零携带入场会连续弹出三个确认框（零装备价值、未装备武备、未穿戴队伍装备）。操作只对**第一个**弹窗做文字识别，确认之后其余弹窗改为按确认按钮是否还在来推进：按钮还在就继续点，按钮消失即认为确认完成。识别过一次之后就不再读提示文字，每轮省掉一次 OCR；点击前的等待也压到最小。未知提示文字仍按原规则停止并保留现场 —— 但只在还没确认过任何弹窗时才读文字，因此这个保护不会因为跳过 OCR 而失效。


### 出生识别与导航

**支持的出生点。** 默认识别录像店、白鸽工地地铁站和单廊双容器三条路线。其他出生点退出重开，不漫游寻找箱子。三条路线各自一份底图和流程，坐标互不通用。

**导航按标定路点逐段行走。** 每条路线把流程拆成若干 `move` 步骤，每步一个路点；到点后按下一步的方向边走边转，长距离路段按住前进不松手，每轮只补一次转向输入 —— 等价于录像里人工的「按住 W 边走边转镜头」。早先的实现每轮松开再点一次前进键（0.2 秒按压 + 0.15 秒等待），走两格就重新定位，视觉上是走走停停，敌人容易追上。实测确认这种点按方式与人工跑法差距明显，已改为连续前进。

**靠近容器用小步直线贴近。** 接近段的 `final_mode` 是 `small_steps`（或隐式默认的 `short_steps`），与最后一段容器的交互距离配合：进入交互范围后松键停稳，不继续前冲。

**出生前确认局内。** 入场操作确认雅努斯高危后，出生检查再次识别普通攻击按钮。单帧模板漏识别时，最多复看 3 帧。持续不符时，出生检查结束并进入[失败收尾](bagel_failure_retry.md#失败收尾)，不计一次出生检查。已确认零投资的入场若在加载期间出现高危死亡结算，也由出生检查进入失败收尾。

**固定小地图定位。** 出生识别、正式导航和开发工具共用固定底图。同次执行使用同一份地图快照，详见[固定地图说明](bagel_fixed_map.md)。

定位失败时，导航停止移动。即使出现路边可拾取物的 F 提示，导航也不能继续前进。重新取得当前帧位置后，导航才允许忽略拾取提示继续移动。导航不提供自动绕障。

**导航等待截图与局内 HUD。** 局内 HUD 指游戏中的常驻状态和操作按钮。导航按以下规则等待：

| 条件 | 处理 |
| --- | --- |
| 动作后的截图尚未更新 | 每隔 0.15 秒等待新截图 |
| 局内 HUD 暂未识别，且未发现暂停菜单 | 先松开前进键，再每隔 0.25 秒检查 |
| 已确认暂停菜单 | 立即失败 |

两种等待均不消耗节点重试次数，但仍受当前导航步骤的整体时限限制。

**录像店复活点导航。** 正式应用先到武备箱，再经巷口、楼角和接近点靠近电子保险箱。路点坐标、切段范围和移动参数以[录像店发布流程](../../../../assets/game_data/bagel/janus_high_a/flow.yml)为准。

接近点允许提前松开按键。导航等待停稳后，用新截图核对位置。仍未到达时，导航在当前步骤内继续短步调整。提前松键本身不能作为到达依据。最终靠近步骤根据当前位置调整，并遵循下文的容器交互规则。导航参数见[开发工具的地图与参数](bagel_flow_editor.md#地图与参数)。

**白鸽工地地铁站复活点导航。** 白鸽路线与录像店共用路点导航。导航按当前位置到下一路点的方向转向，远处连续前进，近处短步调整。路点和移动参数以[白鸽发布流程](../../../../assets/game_data/bagel/janus_high_b/flow.yml)为准。最终靠近步骤使用相同的容器交互规则。

**三张底图是同一片世界，坐标是固定平移。** 用两个定位器跑同一帧录像，统计 `(C坐标 - A坐标)`：

| 录像 | 样本 | dx | dy |
| --- | --- | --- | --- |
| 11:20 | 57 帧 | -178.40 ± 0.56 | -114.29 ± 0.65 |
| 11:58 | 115 帧 | -178.58 ± 0.48 | -114.88 ± 0.96 |
| 12:16 | 97 帧 | -178.42 ± 0.69 | -115.18 ± 0.94 |

三段一致，取 **δ = (-178.47, -114.78)**。任一底图的 `(100,100)` 是它自己的出生点；换算别图的出生点必须加δ，例如录像店出生点在单廊双容器坐标系里是 `(-78.5, -14.8)`。跨图引用坐标时只允许整体加 δ，不得单独改某一个点。

`reference_centers` 里的 `box` / `safe` 是**玩家站位**（交互提示出现时刻的角色位置），不是容器本体，两者相差 4 至 5 格。

**单廊双容器复活点导航。** 这条路线分两段：先从自己的出生点跑到录像店出生点，再执行录像店的固定流程。

转场段的路点取自人工跑通的录像（跑速 15 至 21 格/秒，只在拐点停顿 0.2 至 2.8 秒调镜头），但**不照抄停顿** —— 停顿是人工过弯减速的副产品，快速推进更安全也更省时。路点从录像提取的 11 个转折点精简到 7 段，累计 468 步（约 28 秒）。

相邻路点必须落在实际走过的路径上，且**不能只信栅格的「可通行」**。栅格只能看出可通行像素，看不出实际能不能走：曾据「直线 0 阻挡」把首段写成 178 步直插，实机 5.3 秒只走 7.9 格就撞死在拐角。慢速前进反而更致命 —— 走得慢才会去撞栅格看不见的实物障碍。判据是逐段算「绕行系数 = 直线距离 ÷ 栅格可走距离」，**明显小于 1 才说明两点之间有绕路**；若系数接近 1 但录像显示是折线，说明该段被压缩掉了。

**到达朝向。** 换出生点跑图时，终点路点可以指定 `heading`（角度，图像系 0 为右、90 为下）。到达后导航转到该朝向，对齐后才结束这一步，这样紧接着的固定流程是从与该点开场一致的镜头方向起步。转向期间**保持前进键按下** —— 停步调镜头会被敌人追上；到达朝向与下一步大致同向，边走边转几乎不会偏离终点。转场段的终点（录像店出生点西侧）指定 `heading: 0.0`，即面向地图东侧 —— 这个值取自录像实测：停下时镜头朝西约 184 度，随后原地转到东侧并稳定。未指定朝向的路点行为不变。

**换段先斜着走。** 朝向标记只反映镜头朝向，原地停车转向时人物不动、标记也不变，读数会原地打转。换段时若偏差超过 45 度，改为先按住斜向键走两秒（期间不看标记），让位移把朝向真正带过去；时间到了再读一次标记判断，残留偏差用停车转向微调。斜向组合按「实际移动方向最贴近目标」选择：偏差四十五度用前进加右前斜，九十度用纯右移，一百三十五度用后退加右后斜，一百八十度用后退。

**斜切拐角。** 角色在局内的移动方向等于镜头朝向加上输入方向，所以拐角处不能一律横移 —— 纯横移是相对镜头侧移，镜头朝向不对时会带着角色绕圈走偏。组合的残余夹角都不超过二十五度才执行；目标在身后时不做斜切，改走转向。

斜切与换段斜走都只对[单廊双容器路线](../../../../assets/game_data/bagel/janus_high_c/flow.yml)生效，其余路段沿用原有行为。实机在其他路段横移时曾把角色带出通路，坐标与朝向一起错乱，随即退出。相邻两帧的朝向读数跳变超过一百二十度时只等待重新观测，不做任何移动。

连续两次斜切仍无法转向则判定卡住、松键报失败。

**转向拆步下发。** 单次鼠标事件的位移有有效上限，超出会被游戏丢弃。实测出现过请求转向 148 度、实际只转 0 度的情况：偏差连续 8 次停在同一数值不动，角色原地 14 秒后被敌人追上。控制器因此把大位移拆成多次小步下发，每步不超过 40 像素、间隔 0.012 秒，总量与原请求一致。小角度仍走原来的单次行为。

**转向无响应即停止。** 连续 5 轮转向的偏差都在 30 度以外，判定转向指令没有生效，导航松开按键、报告失败并保留现场。对齐到死区以内会清空该计数，正常的多轮转向不会被误判。

**贴墙卡位停止。** 在电子保险箱远段持续前进时，若匹配位置连续 3 秒未离开 2 像素范围，导航松开按键、报告失败并保留现场。该检查仅限制卡位耗时，不提供自动绕障。

暂停时，导航松开按键并清除卡位计时。恢复后，导航重新校准朝向。暂停时间不计入持续前进时间。

**步骤入口定位暂缺等待。** 出生检查、移动和靠近步骤共用以下规则。局内 HUD 已确认，但当前帧几何证据不足（`insufficient_geometry`）时，执行器每隔 0.3 秒重新截图，最多等待 5 次。

等待期间，执行器不发送移动或交互输入，不推进步骤，也不使用上一帧坐标替代本帧定位。定位恢复后，执行器才运行当前步骤，并清零等待次数。再次初始化也清零等待次数。

持续失配时，执行器结束当前局内步骤。正式应用按[整体重试](bagel_failure_retry.md)收尾，开发工具保留现场。位置冲突、超出底图覆盖范围、裁图错误、出生位置不符和其他画面前提错误，均立即结束步骤。等待不降低定位门槛。

**首次导航定位暂缺等待。** 步骤入口检查通过后，后续截图仍可能无法定位。进入子导航后，在首次取得导航位置前，若新截图仍为 `insufficient_geometry`，导航先松开前进键，再每隔 0.3 秒重新截图。最多等待 5 次，第 6 次仍失配时，导航保留原定位失败状态并停止。

等待期间，导航不移动、不转向、不交互、不切换路点，也不使用入口坐标。取得本帧可靠位置后，导航清零等待次数并继续。再次初始化也清零预算。

位置冲突、超出覆盖范围或非法裁图时，导航直接失败。已经取得导航位置后若连续失配，导航最多等待 3 次，每次间隔 0.15 秒。

### 容器交互与解锁

**交互提示识别。** 交互步骤使用右侧目标提示条，并用模板识别圆形 F 图标。箱子头顶名称不能作为交互依据。局内 HUD、目标提示和 F 图标必须同时出现。搜查面板仍在时，操作不按 F。

**局内判断复用普通攻击按钮。** 入场、出生识别、导航、容器交互、搜查中断和退出，均使用 `战斗画面/按键-普通攻击` 的既有模板和阈值，不读取左侧计分文字。

电子保险箱必须匹配对应交互提示，正式执行器还要求 F 图标。普通武备箱缺少攻击按钮时，操作等待。确认攻击按钮和交互提示后，操作才按 F。已处于解锁或搜查面板时，操作使用对应面板的判据，不补按 F。

**容器停稳确认与开箱恢复。** 武备箱和电子保险箱共用停稳确认、补按 F 和重新靠近规则。流程执行器按容器阶段管理预算。恢复失败后，正式应用进入既有失败结算。开发工具分步试跑仅执行已选动作。阶段边界、完成条件、参数上限和验证范围见[容器恢复说明](bagel_container_recovery.md)。

**电子保险箱光圈解锁。** 正式流程连续执行开箱 F 和光圈解锁。发送开箱输入后，操作立即观察界面，不等待独立步骤交接。确认解锁界面的同一张截图也用于观察光圈。界面出现时，操作记录交互完成并开始解锁。解锁失败归入解锁阶段，由整体失败重试收尾。

开发工具仍按勾选项独立执行交互和解锁。草稿格式和步骤标识保持原样。

光圈操作先观察小圈，再等待红圈或黄圈扩至候选半径。每轮只按 1 次，共 4 次。解锁提示消失时，操作停止输入。完成 4 次点按后，操作仍需等到搜查面板出现，才能确认解锁成功。搜查完成由逐件入箱流程确认。

连续执行消除了固定等待和重复观察造成的空档。开箱按键时长和光圈阈值保持现有值。当前实现没有首轮晚进入补偿，也不识别游戏进度。

**光圈验证范围。** 离线回归覆盖首张小圈只出现 1 次时参与判断、完整 4 轮解锁，以及中断后停止输入。连续开箱时首圈的命中率尚未确认。

### 收集与对换

**容量识别。** 安全箱有 5 个显示位置。识别函数先查找锁定格，再区分占用格和空闲格。仅开放格参与填空、对换和物品计数。开放格必须从左侧连续排列，数量必须符合[安全箱容量范围](../../../game/gameplay/贝果计划.md#备战物资与仓储)。

局内入箱、仓库入仓、启动转存、出售前空箱核验和后续局入场共用此规则。各画面使用各自的格心坐标。

**坐标与缩放。** 局内和仓库使用独立的格心坐标，见[安全箱格子](../../../game/screens/贝果计划.md#安全箱格子)。仓库共用计数入口和启动转存使用同一组仓库坐标。局内默认坐标不能用于仓库核验。

截图控制器默认将游戏窗口截图缩放到 1920×1080。安全箱识别只接收该标准图像，不另做缩放。识别函数拒绝未标准化图像，不表示游戏窗口必须为 1080p。

锁定格通过图标模板识别，不依赖 OCR 读取低对比度的 `LOCK`。截图不完整、模板缺失、格子外观不明或锁定位置不连续时，函数返回未知。操作不处理物品，也不报告清空成功。

**格子识别不受光照影响。** 占用和空槽按「通道归一化后的图案差异度」判定，不直接用灰度标准差。每个像素先除以三通道之和，约掉光照强度，再对三通道两两差的平均求标准差。受击泛红和废弃区光照会整体抬高原始灰度：实测空槽的原始灰度标准差在受击帧会从 8 升到 21，落在原判据 9–20 的区间里，既判不进空槽、又被占用阈值 20 误判成占用，整局因此报「安全箱格子状态不明」。改用归一化差异度后分界稳定：空槽约 4，占用 42–111。差异度的算法不固定通道顺序，传入 RGB 或 BGR 结果一致。

启动转存使用[清空战备的重读上限](bagel_clear_loadout.md)。其他安全箱核验失败时，操作停止并保留现场。满箱后的物品选择见[满箱对换](#满箱对换)。

**验证范围。** 当前识别和流程测试的证据如下：

| 场景 | 测试素材或方式 | 验证限制 |
| --- | --- | --- |
| 四格安全箱的局内识别 | [原生截图](../../../game/screens/贝果计划.md#安全箱格子) | 用于核对局内识别 |
| 两格、三格安全箱和小容量仓库 | 合成测试画面 | 只能验证离线识别，不能证明相应画面的实机执行效果 |
| 720p、1440p 抓图缩放 | 模拟抓图，经真实截图控制器的默认缩放入口后识别 | 对应分辨率尚未由这些测试完成实机验收 |
| 容量识别、入箱、对换、入仓和未知状态保护 | 离线回归 | 小容量安全箱的完整收集和入仓流程尚未完成实机验收 |

仓库合成图以仓库实拍为底，保留仓库格框和背景。测试只在未开放格移植局内实拍的锁图标和文字，不将局内整排格子平移后当作仓库画面。异常分类测试仅保留模板缺失场景。流程测试仍检查未知结果不能继续操作。

**搜查中拾取。** 武备箱或电子保险箱进入「搜查中」后，收集操作开始观察结果格。物品格连续两帧外观稳定时，操作按品质和类型顺序拖入空安全箱。每件物品拖入后都重新读取结果核验。

安全箱满时，操作等待明确的「搜索结果」状态，再判断是否对换，避免误识别动画中的角标。没有可装物品时，操作继续等待。只有明确看到「搜索结果」后，操作才允许关闭面板或退出局内。安全箱满或暂时没有结果均不能作为提前结束依据。

#### 物品识别与优先级

识别函数用格子左右两侧底色判断品质，用左上角标判断类型。颜色和类型说明见[画面文档](../../../game/screens/贝果计划.md#格子)。入箱不按物品名单筛选，而是依次比较以下条件：

1. 非材料物品优先于材料。
2. 同为材料或同为非材料时，按品质排序：`Z > S > A > B > C > 未知`。
3. 非材料品质相同时，依次优先选择贵重物品、战术棱镜、装备、门禁卡、战术道具和其他。

品质和类型优先级均相同时，操作不对换。金币留在搜索结果中，不占安全箱。每次只拖 1 件，再重新读取结果核验。

#### 满箱对换

安全箱满时，操作只用优先级严格更高的搜索结果物品，替换箱内优先级最低的物品。材料可以参与对换。拖拽前后，两格必须确实发生变化。

对换后，原结果格会留下安全箱换出的物品。即使该格的品质和类型发生变化，操作也不再对换该格，避免来回交换。

没有可对换物品时，操作按搜查完成条件关闭面板，不将物品拖入背包，也不记为失败。

#### 搜查状态暂缺与拖拽核验

搜查状态偶尔漏识别时，操作最多等待 5 帧。正式执行器的收集和关闭步骤入口也遵循以下规则：

| 条件 | 处理 |
| --- | --- |
| 对应容器标题仍在，搜查状态暂时漏识别 | 等待期间不发送输入。状态恢复后才运行子操作 |
| 容器标题不符 | 立即停止 |
| 拖拽后等待核验 | 保留原始前后对照，不补拖 |
| 拖拽核验时标题消失，或状态持续漏识别 | 停止 |

#### 拖拽时序

首次入箱、满箱对换和失败后的重拖，统一使用 `duration=0.8`、`press_time=0.1`。鼠标按下后额外等待 0.1 秒，让游戏有时间抓起物品，避免操作变成结果列表滚动。

等待时间独立于移动时长。操作仍需核对拖拽前后两格的变化。完成等待不能作为入箱成功依据。控制器默认值和前后台行为见[拖拽按下等待](../../one_dragon/background_mode_design.md#拖拽按下等待)。

**拖拽没生效时的重试上限。** 核对时若发现源格仍有物品，且目标格仍是拖前那个空格子，说明这次拖拽没有生效，操作最多重拖 3 次，每次都拖向同一个目标格并重新取对照画面。搜出高价值物品时游戏会先播一段加载动画，画面更新滞后于点击，一次重试往往不够；上限用尽后源格物品仍未入箱，操作停止并保留现场，不改投其他格，避免把物品拖到计划外的位置。

**以目标格为准判定入箱成功。** 搜查面板正在关闭时，拖前和拖后的画面差异很大，只看源格是否清空会判错：物品其实已经入箱，却因为源格状态读不准而被当成没拖进去，于是重拖一个已经空掉的格子。操作改看目标格——拖前是空的、现在有物品，就认定入箱成功并计入已装入件数，不再重拖。这条优先于重拖判断，避免把已经入箱的物品又拖出来。

#### 品质与角标识别

品质识别取格子两侧底色的 HSV 中位数。色相范围如下：

| 品质 | 色相范围 |
| --- | --- |
| B | 90–119 |
| A | 120–160 |
| C | 50–85 |

饱和度或亮度低于 40，或色相未匹配色带时，识别函数返回未知，不默认归为 B 或 C。

**角标模板裁剪。** 角标模板按图案轮廓选择位置和尺寸。白色图案必须完整保留，上下左右留白接近。裁剪偏移应通过重新裁剪修正，不能通过降低匹配阈值弥补。

白色箱子的两张模板统一归为材料。未匹配的角标按其他处理。模板类型和尺寸见[贝果画面「格子」](../../../game/screens/贝果计划.md#格子)。

#### 收集与关闭的职责

正式应用和开发执行共用收集行为。搜查完成后，收集操作保留面板，由独立关闭步骤负责关闭。

面板被打断后，子操作停止。正式应用按[搜查中断判据](#搜查中断处理)退出重开，开发工具保留现场。两者均不在原地补开容器。

### 搜查中断处理

收集、关闭搜查或光圈解锁发生可恢复业务失败或实际超时时，执行器读取新截图。只有同时满足以下条件，才判为搜查中断：

- 已回到贝果局内。
- 武备箱和电子保险箱的搜查面板均已消失。
- 解锁提示已消失。

步骤入口已被打断时，执行器使用同一判据。正式应用按[整体重试](bagel_failure_retry.md)退出到仓库，核对安全箱物资入仓后，再决定是否重开。中断局不计成功。

未知画面、面板仍在时的拖拽错误，以及退出或入仓失败，均停止。开发工具只返回中断状态，不自行退出或补开容器。

### 入仓核验

点击「放入仓库」后，操作同时核对安全箱和仓库占用。仓库「全部 N/M」中的 N 表示占用，M 表示当前界面显示的实际容量。M 不能固定取 280。下表中的占用变化均与点击前读数比较。

| 结果 | 判定与处理 |
| --- | --- |
| 安全箱清空，N 增加 | 入仓成功。包括占用从 `(M−1)/M` 增至 `M/M`，恰好满仓的情况 |
| 安全箱清空，N 不变，且 N<M | 入仓成功。允许物品合并到已有堆叠 |
| 安全箱清空，N 不变，且 N≥M | 停止。不能凭堆叠推测物资已入仓 |
| 安全箱清空，但 N 下降或必要读数无法核对 | 停止，不计入仓成功 |
| 安全箱只减少部分格子 | 立即停止，不重复点击，也不继续清理 |
| 安全箱格子完全未变 | 允许有限重试或判满仓 |
| 安全箱仍占用，且 N≥M 连续 6 帧 | 记为仓满并停止 |

安全箱仍有物资时，常规清理禁止批量出售并保留现场；仓满强制腾位时按上面的基线口径处理。入仓核验不按物品名称判断。

入仓成功后，正式应用按清理开关处理仓库，再执行[出售与结算核验](#出售与结算核验)。仓库未满才允许结束结算并返回入口。入仓后恰好满仓时，正式应用仍可进入清理流程。

### 仓库清理与返回

#### 出售方案

清理开关默认开启。关闭时，正式应用只执行入仓。出售按以下方案选择：

| 方案 | 类型 | 品质 |
| --- | --- | --- |
| 默认 | 贵重物品、战术棱镜、其他。不选装备、战术道具和门禁卡 | C/B/A/S。不选 Z |
| 自定义 | 使用配置中选择的类型，不能为空 | 使用配置中选择的品质，不能为空 |

快速选择中的类型和品质必须同时匹配，物品才会进入出售范围。「全部」始终不选。操作每次重新读取所有选项，并取消方案未选的项目。清理流程不点击整理，也不自动转化货币。

**出售频率。** 配置项 `clean_interval` 是大于等于 1 的整数，默认 1 表示每个成功入仓局都出售；设为 5 表示每 5 局卖一次。每次真的卖出后重新计数，所以间隔稳定。空箱局不计数，因为没有东西可卖。关闭自动清理时这个参数不起作用。

**仓库已满时强制腾位。** 仓库格数不够时，安全箱里的物资入不进去，这是预期情况，不按「物资去向不明」处理。操作先确认是否已满，确认满后在入仓节点就无视清理开关直接出售，把格位腾出来后再结束本局 —— 下一局拿到的物资才放得下。腾位失败才停止并保留现场。

腾位模式允许安全箱非空。仓满是唯一会用到腾位的场景，而仓满的成因就是安全箱里的物资放不进去；此时若仍要求安全箱为空，「仓满 → 腾位 → 要求安全箱为空」会变成无解的死循环。腾位前记下安全箱的占用格作为基线，出售后要求占用格与基线完全一致 —— 不是要求清空，而是要求一件都没动。快速选择只作用于右侧仓库格，安全箱不在出售范围内。

腾位和入仓是一个来回：腾出格位后必须补一次入仓，否则只是腾了位、本局物资仍在安全箱里，成功局数也不该计。一轮腾位通常只卖出少量物品，腾出的格数不够放下安全箱里的全部物资，所以按「腾位 → 补入仓」循环，最多 5 轮（安全箱最多 5 格，每轮至少空出 1 格，5 轮足够）。方案内没有可出售物品时立刻停止，不再空转补入仓。补入仓时若读到安全箱为空，说明物资去向不明，同样停止。

**空箱局一律不出售。** 安全箱入仓前就是空的时候，本局零收获，不进入批量出售流程，出售方案（默认或自定义）都不生效。空箱是独立终态：既不打开批量出售，也不做仓满核验，直接结束本局结算。空跑一趟出售本身没有必要，更关键的是此时仓库里存着前几局攒下的物资，一旦快速选择点错就会把存货卖掉。判定依据是入仓前的安全箱占用格数，与清理开关和出售方案无关。

#### 出售与结算核验

1. 在仓库主界面确认安全箱状态：常规清理要求为空；仓满强制腾位时记下占用格作为基线，随后核对它一件未动。
2. 核对筛选件数。件数为 0 时，操作确认筛选后取消出售。有可出售物品时，操作进入出售预览并确认。
3. 出售后，操作确认安全箱与出售前一致（常规为空箱，腾位时为基线占用格），且仓库占用下降。不满足时，操作不能报告清理成功。
4. 结算末尾，操作用新截图再次确认安全箱为空，且仓库占用小于容量。清理关闭或没有可出售物品时，也执行该核验。

结算末尾仍满仓时，正式应用停在仓库，不计成功，也不返回入口。

**返回时的页面阻挡。** 仓库返回时先等待加载结束，再按 F 与达塔交互，打开贝果主界面。后续各局直接从主界面选图。返回加载和点击「出发出发」后的切换黑屏均继续等待；单凭连续未识别到 HUD 不触发恢复。恢复触发条件和等待上限见[整体重试说明](bagel_failure_retry.md#页面阻挡恢复)。确需通用恢复时，正式应用随后重新检查入场条件。页面恢复不改变任务计数或首次清空资格。

**返回时的奖励提示。** 结算仓库点击「返回研究站」后，若同时识别到「撤离奖励提示」和奖励转移说明，返回操作只确认 1 次，再等待研究站 HUD。

## 3. 配置（`BagelConfig`）

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `max_success_rounds` | 1 | 成功局数上限，范围为 0–1000。0 表示不限成功次数。非支持出生点和失败局不计数 |
| `max_failure_retries` | 5 | 累计整体重试次数上限，范围为 0–100。最多因失败额外重开 N 局，成功后不清零 |
| `auto_clean_warehouse` | 开 | 关闭时只入仓，开启时按方案出售 |
| `clean_mode` | `default` | `default` 使用固定组合。`custom` 使用下面两组选择 |
| `clean_types` | 空 | 自定义出售类型。可选贵重物品、战术棱镜、其他、装备、战术道具和门禁卡，不含「全部」 |
| `clean_qualities` | 空 | 自定义出售品质。可选 C/B/A/S/Z |

任务配置页位于主窗口内，可以滚动。设置自动保存，并绑定当前账号和应用组。进入页面加载配置时，页面不写回配置。

| 条件 | 显示的设置 |
| --- | --- |
| 始终 | “成功次数”“整体重试次数”“清理仓库” |
| 开启清理 | 出售方案 |
| 开启清理且选择自定义方案 | 出售类型和品质，两者均须非空 |

### 开发工具与发布流程

`flow.yml` 是正式业务步骤和路点的唯一来源。`BagelApp` 启动时加载不可变流程快照，并调用与开发工具相同的 `BagelRunFlow`。外层应用负责入场、结算、清理和重开。

开发草稿不影响正式任务。只有导出正式流程才会修改发布资源。

开发工具从源码独立启动，普通设置页不提供入口。启动命令、步骤编辑、参数、保存和文件导入说明见[贝果流程开发工具](bagel_flow_editor.md)。地图资源和坐标规则见[固定地图说明](bagel_fixed_map.md)。

### 执行与输入清理

正式应用和操作基类为每次执行分别包装暂停、恢复回调。执行结束时，清理按以下顺序进行：

1. 停用本次执行的订阅。
2. 等待已开始的回调完成。
3. 从运行总线解绑。

初始化或收尾异常也使用该清理流程，避免上一次执行的回调影响下一次执行。

局内执行器和开发试跑共用输入清理函数。暂停和收尾时，函数重置持续按键，并额外释放定时前进、交互和鼠标拖拽。后台拖拽还向游戏窗口发送左键松开消息。清理不会取消正在执行的拖拽循环。

## 4. 使用前置

- 研究站和「迷宫诡域」传送点已解锁。
- 从普通大世界、地图、菜单、快捷手册、普通仓库、达塔对话或贝果入口启动。
- 雅努斯高危允许零携带、零投资入场。
- 跑图角色和镜头设置会影响位移。更换角色后，需要检查路线是否仍可通行。

## 5. 功能限制

- 入箱不按物品名称和等级筛选，也不记录按名单收集的进度。
- 收集操作不拾取金币，不将携带货币计入已入仓物资。货币退出保留规则见[玩法文档](../../../game/gameplay/贝果计划.md)。

测试位于独立仓 `zzz-od-test/test/zzz_od/application/bagel/`。运行方式见[测试文档](../../testing/README.md)。
